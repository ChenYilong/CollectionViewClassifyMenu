# Verify changes

CI (`.github/workflows/ios.yml`, modelled on CYLTabBarController) runs the same
scripts on a macOS runner. Locally, on a Mac with Xcode and CocoaPods, run the
smallest checks relevant to the change:

```sh
scripts/unit-tests.sh menu       # CollectionViewClassifyMenuTests
scripts/unit-tests.sh tag        # TagCollectionView tests
scripts/unit-tests.sh example    # Example (CYLTagListView API and README scenarios)
scripts/unit-tests.sh swift      # Example-Swift (pure Swift tag editor: new tags)
scripts/library-warnings.sh      # build + analyze; fails on warnings in the library sources
scripts/pod-lint.sh lib          # pod lib lint
scripts/cyl-tabbar-latest-commit.sh --check   # the CYLTabBarController pin is its newest commit (before building)
scripts/example-screenshots.sh   # simulator screenshots in build/screenshots/ (swift-*.png: Example-Swift)
shellcheck scripts/*.sh
```

`unit-tests.sh example|swift` also writes the screenshots the tests record (`CYLScreenshotCapturing`) to
`build/test-screenshots/<suite>/`; look at them and copy the ones the README shows to `assets/test-*.png`.
Stitch and label screenshots for `docs/` or the README with `.agents/skills/cyl-screenshots/SKILL.md`
(one column, two when taller than a phone screen; header and footer with the purpose and the test environment).

Apps built with the iOS 27 SDK (Xcode 27) must adopt the scene lifecycle, otherwise UIKit stops them at launch
(`_UIApplicationEvaluateRuntimeIssueForNoSceneLifecycleAdoption`, "The test runner crashed before establishing
connection"). Both examples and both root demo apps (the hosts of `menu` and `tag`) have a scene delegate; test windows
join the app's scene (`CYLWindowHosting`). `simulator-id.sh` without a name may pick a new device type (such as
"iPhone Duo") whose tab bar is not at the bottom; pass "iPhone 17 Pro" to compare with earlier runs.

## Fix issues in the core first

- The core is the code published to a package registry: the CocoaPods pod / Swift package, the Maven / Gradle
  libraries (`android/merged/library`, `android/AndroidTagView/androidtagview`), the npm package
  `react-native-cyl-tag-list` (not its examples), the pub.dev plugins (not their `example/`), the ohpm HAR
  `harmony/classifymenu` (not `harmony/entry`) and the mini program packages. Everything else is the example layer.
- Fix every issue or bug in the core first, even one seen only in an example screenshot, so that every app using the
  library and every similar case is fixed. Look for the core cause (a default, a missing option, a layout or
  measurement rule, a missing localization or accessibility hook, a color that ignores the color mode) before
  touching the example.
- An example-layer fix is the worst option: only for a defect that really is in example code or data (a demo string,
  a demo page's own layout, a screenshot script), or when the core cannot fix it.
- When a core defect cannot be fixed in the core: ask the user first and say why (a third-party bug, a platform
  limitation, an API kept for compatibility).
- Record every example-layer fix in `docs/example-layer-fixes.md` (issue, files, why not in the core) and mention it in
  the issue's progress-table row. Full rule: AGENTS.md "Fix issues in the core first".

## Parity tables and the score loop

- Parity tables and the score loop (AGENTS.md "Parity tables and the score loop"): source API | description | counterpart (`TODO` by default); 100 when no `TODO` is left, 0 when all are; loop: match existing code, score, implement the `TODO` rows in the core first and show them in the example, score again, until 100; then the reverse table.
- Generated tables (`docs/android-ios-api.md`, `docs/android-api.md`) are regenerated by their scripts, never edited by hand.

## Bugs: record, screenshot, fix upstream

- Bugs (AGENTS.md "Bugs: record, screenshot, fix in CYLTabBarController's animated item"): record first, then screenshot, then fix; animation and icon + title bugs are fixed in CYLTabBarController's animated item component, not in the examples; a demo that needs more gets a new component API from CYLTabBarController.

## Running scripts

- **Run scripts with bash, not the interactive shell.** Shell scripts and multi-line command sequences run in bash:
  `bash path/to/script.sh`, or `bash <<'EOF' … EOF` (or `bash -c '…'`) for an inline sequence; new scripts start with
  `#!/usr/bin/env bash` (a POSIX `#!/bin/sh` script is run with `sh` or `bash`, never sourced into zsh). The
  interactive shell on macOS is zsh, which behaves differently: it does not split an unquoted `$var` into words
  (`box="10 20 30 40"; set -- $box` gives one argument, so a measurement over `$box` silently reads one value), a
  variable holding a command with its arguments (`hdc="hdc -t 127.0.0.1:5563"; $hdc shell …`) fails with "no such
  file or directory", and a glob that matches nothing aborts the whole command. The error this rule prevents: "zsh
  doesn't split $box into words either. Running the same measurement as a bash script." Keep a command with
  arguments in a wrapper script or a bash array (`hdc=(hdc -t 127.0.0.1:5563); "${hdc[@]}" shell …`), never in a
  string variable.

  <https://github.com/ChenYilong/CYLTabBarController/blob/master/.github/workflows/ios.yml>, and the same file at

## Screenshots (build, CI/CD and local)

The same rules as AGENTS.md, "CI/CD and Example screenshots":

- **Screenshots: where they go.** Every screenshot, from CI/CD and from local builds alike, is saved in the
  Git repository and shown in the related document in `docs/` (images in `docs/assets/`); when no document fits,
  create one (the default is `docs/screenshots.md`). At the right moment, when you judge that the result looks as
  expected, update `README.md` with the newest images, in the matching section (create it if missing).
- **Screenshots: labels.** Every screenshot shown in `docs/` or `README.md` is labeled with:
  - the platform it ran on: iOS, Android, Flutter, React Native, HarmonyOS or Mini Program;
  - the environment: the operating system version, the simulator / emulator version, and the platform's SDK version
    (iOS, Android, Flutter, React Native, HarmonyOS or Mini Program SDK);
  - this repository's version number or commit URL;
  - the current time (when it was taken).
- **Screenshots: quality.** Use clear original images; never downscale or recompress them.
- **Screenshots: key moments.** Update the README images at key moments: for example when a `TODO` keyword or a
  `Linux` keyword can be removed, when a pull request can be merged, or when you judge the result as expected, with
  no bug and no open issue.
- **Screenshots: crop to the detail.** Screenshots in `README.md` show the key details, cropped; do not use
  full-screen captures unless necessary. Prefer one stitched image that shows several key details.
- **Screenshots: stitching layout.** Stitch in this order of preference: (1) stacked vertically, top to bottom, which
  reads best on a phone; (2) two columns, several rows; (3) last resort, side by side in one row, at most three
  columns per row. Correction (2026-11-12): the original request said both "prefer a horizontal layout" and "a horizontal stitch is the worst", which contradict each other; the user corrected it to vertical first.

## Stop the simulator when the run is done

Before you run a simulator, read "Simulators and emulators: stop them when the work is done" in
`docs/instructions/sessions.md`. After the tests or screenshots, immediately terminate the app and shut the simulator down:
your own devices only (`xcrun simctl terminate <udid> <bundle id>`, `xcrun simctl shutdown <udid>`), by UDID, never
`shutdown all` or a broad `pkill`; boot again for the next run. Report "stopped: <udids>".
