## scripts/bilingual-docs.py

Bilingual Chinese-English Markdown (docs/Bilingual-Documentation.md): extract, assemble and check.
extract FILE [-o UNITS.json]            split FILE into the passages that need a translation
assemble FILE UNITS.json TRANSLATIONS.json [-o OUT]
build the bilingual layout; code, images, links and table structure are kept
check FILE... [--against GIT_REF]       check the layout; with --against also that code blocks, inline code, links
and images equal those of the same file at GIT_REF (nothing but text changed)
A table, list or paragraph right after `<!-- bilingual:keep -->` is generated data (code names, a score history) and stays as is.
Layout (CYLTabBarController's bilingual standard): a heading is one line "Chinese / English"; prose (a paragraph or a
list item) is one row of a two-column table, Chinese left and English right; a table with more columns is given twice,
a Chinese table and then its English twin; code blocks, HTML, comments and images are shared.
TRANSLATIONS.json maps a unit id to {"zh": ..., "en": ...}: only the language the unit lacks is needed (the other is the
source text itself); a unit that mixes both languages needs both. Python 3 standard library only.

## scripts/check-doc-comments.py

Usage: scripts/check-doc-comments.py [--fix] [header ...]
Public API documentation comments (AGENTS.md, "Code comments"; .agents/skills/cyl-comments): every comment that
documents a declaration in a public Objective-C header, one line or several, is one /*! ... */ block, so the file
has one comment format and Xcode's Quick Help and the Swift interface show it: three lines (/*!, " * text",
" */") above the declaration, never /*! text */ on one line and never a trailing comment. Lists /// lines (single
or stacked), /** openers, plain // comments placed on a declaration, one-line /*! text */ blocks and trailing
comments (/**< */, /*!< */, ///<, //) after a declaration or an enum value in the pod's public headers (or the
given headers) and exits 1 when there are any; --fix rewrites them as three-line /*! ... */ blocks above the
declaration.
使文件内注释格式统一，Xcode 快速帮助与 Swift 接口都能显示：在声明上方写三行（/*!、" * 文字"、" */"），不把 /*! 文字
写在一行，也不在声明或枚举值后写尾随注释。列出 pod 公开头文件（或指定头文件）中的 /// 注释（单行或堆叠）、/** 开头、
写在声明上的普通 // 注释、单行的 /*! 文字 */ 以及声明或枚举值后的尾随注释（/**< */、/*!< */、///<、//），
存在时退出码为 1；--fix 将其改写为声明上方的三行 /*! ... */ 注释块。

## scripts/check-localization-ports.py

Checks the localization of the Android, HarmonyOS and mini program ports, the twin of scripts/check-localization.py
(iOS, Flutter, React Native; AGENTS.md "Internationalization and localization").
Usage: python3 scripts/check-localization-ports.py
Every table these ports read is an iOS table, or a file generated from one (Android reads the iOS bundles as assets;
HarmonyOS `CYLExampleStrings.ets` / `CYLCoreStrings.ets` and the mini program `strings.js` / `core-tables.js` are
exported from them). check-localization.py checks those tables (same keys in every language, format specifiers). Here:
1. code: a Chinese literal is a lookup's argument, a key of the iOS tables (stored and looked up later), or marked
NOLOCALIZE (on its line, or between NOLOCALIZE-BEGIN and NOLOCALIZE-END): user content and sample data that stay as
written (reviews, product titles, the places database's source titles, deliberately multilingual sample tags);
2. the ports' own tables (Android `res/values*`, HarmonyOS `resources/*/element/string.json`): the same names in every
language, no Chinese in the English (default) table, and no Simplified-only character in the Traditional Chinese
table. Simplified-only characters are learned from the iOS tables: where a key (Simplified) and its zh-Hant value
differ at the same position, the key's character is Simplified-only.
Exits 1 when anything is found.

## scripts/check-localization.py

Checks the iOS string tables against the code that looks them up (AGENTS.md "Internationalization and localization").
Usage: python3 scripts/check-localization.py [--unused]
For every module (core, demo app, Example, Swift Example):
1. every key passed as a literal to the module's lookup exists in every translated language of its bundle
(Example bundles: en and zh-Hant; their keys are the Simplified Chinese source, so zh-Hans needs no entry);
2. every translation keeps the key's format specifiers (%@, %ld, %d, ...), in order;
3. no Chinese string literal is shown without the lookup: a literal with Chinese characters outside a lookup call
and a comment that is not a key of every table (keys stored and looked up later pass) is reported, unless its line
says NOLOCALIZE, or it sits between NOLOCALIZE-BEGIN and NOLOCALIZE-END comments: user-generated content and sample
data that stay as written (reviews, a shop's product title, song names, deliberately multilingual sample tags);
4. with --unused, keys no code mentions are listed (keys built at run time are reported too, so review by hand).
5. the Flutter and React Native examples: a Chinese literal is a lookup's argument, a key of their generated tables
(exported from the iOS bundle), or marked NOLOCALIZE.
Exits 1 when 1-3 or 5 find anything.

## scripts/check-path-length.sh

Fails when a tracked path is longer than MAX characters (default 160).
Windows limits a full path to 260 characters; this repository is often cloned into deep folders such as
"C:\Users\<name>\OneDrive - <org>\Documents\GitHub\CollectionViewClassifyMenu\" (about 90 characters), so a path
longer than about 170 characters inside the repository makes `git checkout`, `git worktree add` and `git stash`
fail with "Filename too long". 160 keeps a margin.

## scripts/check-screenshots.py

Fails when a screenshot added or changed in docs/assets/ or assets/ is not stitched and labeled by the rules.
AGENTS.md "CI/CD and Example screenshots": every screenshot shown in docs/ or README.md has a header (Purpose,
Platform, Host, IDE), a caption above every panel and a footer (Result, Versions, Taken). Images are made with
scripts/stitch-screenshots.py (any host) or scripts/stitch-screenshots.swift (macOS); both write the header and footer
into the PNG's "Description" text chunk, starting with "cyl-stitch-screenshots". This check reads it back.
python3 scripts/check-screenshots.py                # the staged files (before a commit)
python3 scripts/check-screenshots.py --range A..B   # the files a range changes (base..head)
python3 scripts/check-screenshots.py FILE ...       # these files
Exit 0: every image passes (or none changed); 1: at least one does not, with the reason and the fix.
Images that are not screenshots (a diagram, an icon) or that a script regenerates are listed, with the reason, in
scripts/screenshot-check-exempt.txt (one glob per line).

## scripts/stitch-screenshots.py

Stitches labeled screenshots by the rules of AGENTS.md ("CI/CD and Example screenshots"), on any host.
The cross-platform twin of scripts/stitch-screenshots.swift (macOS only), with the same arguments:
python3 scripts/stitch-screenshots.py --out docs/assets/<name>.png [--columns auto|1|2] [--crop x,y,w,h] \
--header "Purpose: ..." --header "Platform: ... | Host: ... | IDE: ..." \
--footer "Result: ..." --footer "Versions: ..." --footer "Taken: ... | Stitched by scripts/stitch-screenshots.py" \
"1. <caption>::<image>" "2. <caption>::<image>" ...
Layout: one column first, panels top to bottom; two columns (left to right, then top to bottom) when the one-column
image would be taller than one phone screen (height > 19.5 / 9 x width); never more than two. A header band above the
panels, a footer band below them and a caption band above every panel; no text is drawn on a screenshot. The panels
keep their original pixels (no scaling); --crop cuts the same rectangle out of every image (crop to whole elements).
The label is required, not optional: the tool stops when the header lacks "Purpose:", "Platform:", "Host:" or "IDE:",
when the footer lacks "Result:", "Versions:" or "Taken:", or when a panel has no caption. It writes the header and
footer into the PNG (text chunk "Description", starting with "cyl-stitch-screenshots"), which
scripts/check-screenshots.py checks before a commit.

## scripts/stitch-screenshots.swift

Usage (macOS; on any host: scripts/stitch-screenshots.py, same arguments): swift scripts/stitch-screenshots.swift --out <file.png> [--columns auto|1|2] [--crop x,y,w,h]
           --header <line> [--header <line> ...] --footer <line> [--footer <line> ...]
           "<caption>::<image>" ["<caption>::<image>" ...]
Stitches screenshots by the rules of AGENTS.md ("Screenshots: stitching layout, update", "Screenshots: header and
footer"): one column first, panels top to bottom; two columns (filled left to right, then top to bottom) when the
one-column image would be longer than one phone screen, i.e. taller than 19.5:9 (height > 2.17 x width, the shape

band above the panels, a footer band below them and a caption band above every panel. No text is drawn on a screenshot:
every band has its own space. The panels keep their original pixels (no scaling); `--crop` (pixels, top-left origin)
cuts the same rectangle out of every image, so crop to whole elements. Output: PNG.

## scripts/swift-api-check.sh

Usage: scripts/swift-api-check.sh [--baseline]
Checks that the Swift migration of the core (docs/Swift-Migration.md) keeps the Swift API that callers see:
builds the CollectionViewClassifyMenu pod (Example-Swift workspace, clean derived data), dumps its API with
swift-api-digester and compares it with scripts/swift-api-baseline.json (the API of the Objective-C core).
CocoaPods' module map puts every header in a submodule, which swift-api-digester does not read, so the dump uses a
copy of the framework whose module map has no submodules.
--baseline   writes the dump as the new baseline instead of comparing.
Prints the API breakages (removed or renamed declarations, changed types) and exits 1 when there are any.

## scripts/swift-migrate-pbxproj.py

The root CollectionViewClassifyMenu.xcodeproj lists the core's files in its groups (the pod compiles them). After
